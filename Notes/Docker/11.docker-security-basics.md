# Docker Security Basics

## Overview
Container security focuses on reducing the attack surface and limiting privileges.

## Key Concepts

### Run as a non-root user
- Avoid running containers as root whenever possible.
- Create a dedicated user in the image and use `USER` in the Dockerfile.

```dockerfile
FROM python:3.11-slim
RUN useradd -m appuser
USER appuser
```

### Read-only filesystem
- Use a read-only root filesystem when the app does not need to write to disk.
- This reduces the chance of tampering or accidental changes.

```bash
docker run --read-only alpine:latest sh
```

### Minimal images
- Use smaller base images such as `alpine` or `distroless`.
- Remove unnecessary packages and build artifacts.

### Pin image versions
- Avoid relying on floating tags like `latest` in production.
- Use specific versions such as `nginx:1.27.0` to reduce surprise changes.

### Limit container privileges
- Drop unnecessary Linux capabilities.
- Use `--security-opt no-new-privileges` to prevent privilege escalation.

```bash
docker run --cap-drop ALL --security-opt no-new-privileges myimage
```

- In docker-compose, you can drop capabilities like this:

```yaml
 cap_drop:
      - ALL 
#cap_add:
   #  - NET_ADMIN  -> Add if you need to add capabilities
```

### Protect secrets
- Never hardcode secrets inside Dockerfiles or source code.
- In a real application, secrets are usually passed at runtime through environment variables, Docker secrets, or a secret manager.
- This keeps sensitive values out of the image layer and makes them easier to rotate.

#### Best Practices for Managing Secrets

**1. Use Environment Variables (Simple applications)**
- Pass secrets at runtime, not at build time.
- Keep `.env` files out of version control by adding to `.gitignore`.

```bash
export API_KEY="super-secret-value"
docker run -e API_KEY="$API_KEY" myapp:1.0
```

**2. Docker Compose with `.env` files**
- Store secrets in a `.env` file (not in git).
- Reference them in `docker-compose.yml`.

`.env` file:
```
API_KEY=super-secret-value
DB_PASSWORD=db-secure-pass
```

`docker-compose.yml`:
```yaml
services:
  app:
    image: myapp:1.0
    environment:
      API_KEY: ${API_KEY}
      DB_PASSWORD: ${DB_PASSWORD}
```

**3. Docker Swarm Secrets (Encrypted storage)**
- Ideal for multi-node cluster deployments.
- Secrets are encrypted and stored in the Raft consensus log.
- Automatically mounted inside containers at `/run/secrets/`.

```bash
# Create a secret
echo "super-secret-value" | docker secret create api_key -

# Use in compose
services:
  app:
    image: myapp:1.0
    secrets:
      - api_key
    environment:
      API_KEY_FILE: /run/secrets/api_key

secrets:
  api_key:
    external: true
```

Access in your application:
```python
# Python example
with open('/run/secrets/api_key', 'r') as f:
    api_key = f.read().strip()
```

**4. Mount Secret Files (Production approach)**
- Mount secrets as read-only files rather than environment variables.
- Prevents secrets from appearing in `docker inspect` or environment variable listings.

```bash
docker run -v /path/to/secret.txt:/run/secrets/api_key:ro myapp:1.0
```

Docker Compose:
```yaml
services:
  app:
    image: myapp:1.0
    volumes:
      - ./secrets/api_key:/run/secrets/api_key:ro
```

**5. External Secret Managers**
- Use HashiCorp Vault, AWS Secrets Manager, or similar tools.
- Application fetches secrets at runtime from a secure store.
- Best for enterprise and highly sensitive deployments.

```python
# Example: App fetches from Vault at startup
import requests

def get_secret(secret_path):
    response = requests.get(
        f"http://vault:8200/v1/secret/{secret_path}",
        headers={"X-Vault-Token": os.getenv("VAULT_TOKEN")}
    )
    return response.json()
```

#### Key Security Rules

- **Don't store secrets in images**: Use build arguments for non-sensitive data only.
- **Never log secrets**: Sanitize logs to prevent accidental leakage.
- **Rotate secrets regularly**: Change credentials on a schedule.
- **Use read-only mounts**: Prevent containers from modifying secret files.
- **Separate secrets by environment**: Different keys for dev, staging, and production.
- **Restrict file permissions**: Ensure secret files have restricted access (600 or 400).

```bash
# Secure secret file permissions
chmod 600 secrets/api_key
chmod 400 secrets/db_password
```

- **Don't pass secrets in docker run commands**: They appear in process lists and command history.
- **Use secrets from files, not command arguments** to avoid exposure in logs.

### Restrict network exposure
- Expose only the ports your application truly needs.
- Prefer custom networks over publishing everything to the host.

```bash
docker run -p 8080:80 myimage
```

### Apply resource limits
- Set memory and CPU limits to reduce the impact of abuse or misconfiguration.

```bash
docker run --memory 256m --cpus 0.5 myimage
```

## Useful Commands

```bash
docker run --user 1000:1000 myimage
docker run --read-only myimage
docker inspect <container>
docker scan myimage
```

## Hardened Example

```bash
docker run -d --name app \
  --user 1000:1000 \
  --read-only \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --memory 256m \
  --cpus 0.5 \
  myimage:1.0
```

Normally, the root user gets a master key with 40+ specific master keys attached to it—keys to reboot the system, change network settings, read any file, or control hardware.

By default, Docker takes away some of those keys, but still hands your container about 14 master keys.

What cap_drop: ALL Does

cap_drop: ALL takes away every single key on that keyring.

- Without cap_drop: If a hacker breaks into your Python app, they hold 14 master keys. They can tamper with the network, kill other processes, or try to hack the main server.

- With cap_drop: ALL: The hacker gets zero keys. They are trapped in a room with no privileges to do anything outside of running your basic Python code.

## Insights
- Security hardening should be done gradually.
- Not every container can be fully read-only, so evaluate app requirements first.
- Small, minimal images, least-privilege execution, and secret protection are best practices.
