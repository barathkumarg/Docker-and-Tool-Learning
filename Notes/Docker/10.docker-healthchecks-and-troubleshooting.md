# Docker Health Checks and Troubleshooting

## Overview
Docker health checks help you know whether a container is truly ready to serve traffic, not just whether it is running.

A container can be "up" but still unhealthy if its app is not responding correctly.

## Key Concepts

### Health checks
- A health check runs a command inside the container.
- It returns success or failure based on the result.
- Docker can mark the container as healthy or unhealthy.

### Common commands
- `docker compose ps` — view service status.
- `docker ps` — view container status and health.
- `docker inspect <container>` — inspect health check configuration.
- `docker logs <container>` — view startup or runtime errors.

## Example Health Check

### Dockerfile example
```dockerfile
FROM nginx:alpine
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD wget --spider http://localhost/ || exit 1
```

### Compose example
```yaml
services:
  web:
    build: .
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:80/"]
      interval: 10s
      timeout: 5s
      retries: 3
```

## What Health Checks Actually Do

A health check answers one important question:

- Is this container really ready to serve requests?

A container may be running, but the application inside it might still be starting up, blocked by a dependency, or failing silently.

Health checks help with this by running a small test inside the container, such as:

- checking an HTTP endpoint
- testing a database connection
- verifying a local service responds correctly

If the test passes, Docker marks the container as healthy. If it fails repeatedly, Docker marks it as unhealthy.

## Why This Is Useful in Production

In production, health checks are important because they help automate safe deployments and recovery.

### Real-world use cases
- Load balancers can avoid sending traffic to unhealthy containers.
- Rolling updates can wait for the new version to become healthy before replacing the old one.
- Auto-restart and orchestration tools can react faster when a service is unhealthy.
- Teams can detect broken startup behavior before users notice it.

### Example production scenario
Imagine an API container starts but its database connection is not ready yet.

Without health checks:
- the container might appear to be running
- traffic could be routed to it too early
- requests may fail randomly

With health checks:
- Docker notices the app is not ready yet
- the service stays unhealthy until the dependency is available
- the deployment becomes safer and more predictable

## Production-Style Example

```yaml
services:
  api:
    build: .
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s
```

This means:
- try the health check every 10 seconds
- fail after 3 repeated issues
- wait a short startup period before the first check

## Troubleshooting Checklist

1. Check container status with `docker ps`.
2. Inspect health details with `docker inspect`.
3. View logs with `docker logs`.
4. Verify the internal port and endpoint.
5. Fix the application or configuration and restart the container.

## Useful Commands

```bash
docker compose up -d
docker compose ps
docker inspect <container_name>
docker logs <container_name>
docker restart <container_name>
```

## Insights
- Health checks are useful for web servers, APIs, and databases.
- A health check should test a real app condition, not just the process state.
- In production, health checks improve reliability, safer rollouts, and faster failure detection.
- They are especially valuable when services depend on databases, caches, or other containers.
