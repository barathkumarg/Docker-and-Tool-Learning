# Docker Network

## Overview
Docker networking lets containers talk to each other, to the host, and to the outside world.

When Docker starts, it usually creates a default bridge network called `docker0` on Linux. This is a virtual network interface on the host.

- Each container gets its own virtual network interface inside the container.
- Docker connects that interface to the host bridge `docker0`.
- The container gets an IP address on the bridge network, for example `172.17.0.2`.
- Containers on the same bridge can reach each other.

### How internet access works
- The container sends traffic to the host through `docker0`.
- Docker uses NAT (network address translation) to map container traffic to the host IP.
- The host then forwards traffic to the internet.
- For most containers, outbound internet access works automatically as long as the host has internet access.

### Host and container story
- In the default `bridge` mode, the container has its own isolated network namespace.
- `docker0` is the host side of the bridge, and the container side is a virtual interface like `eth0` inside the container.
- The host and container can communicate through this bridge.
- In `host` mode, the container does not get its own network namespace: it uses the host network directly.
  - This means no `docker0` isolation, and ports are the same as the host.
  - It is faster but less isolated.

## Network Types

- bridge: Default network driver for standalone containers. Provides isolation between containers and the host. Containers on the same bridge network can communicate using container names.
- host: Removes network isolation between the container and the Docker host. The container shares the host's network stack.
- overlay: Enables containers across multiple Docker daemons to communicate; used in swarm mode.
- macvlan: Assigns a MAC address to a container, making it appear as a physical device on the network.
- none: Disables all networking for a container.

## Creating Networks

```sh
# Create a user-defined bridge network
docker network create my_bridge

# Run containers attached to the network
docker run -d --name app1 --network my_bridge myapp:latest
docker run -d --name app2 --network my_bridge myapp:latest
```

## Inspecting Networks

```sh
docker network ls
# Lists all networks
docker network inspect my_bridge
# Shows details about a specific network
```

A typical `docker network ls` output looks like this:

```
NETWORK ID     NAME       DRIVER    SCOPE
6233f1e7ecce   bridge     bridge    local
f592974e0aba   host       host      local
```

- `NETWORK ID` is the internal identifier for the network.
- `NAME` is the network name Docker uses.
- `DRIVER` shows how the network behaves.
  - `bridge` is the default isolated network for containers.
  - `host` means containers share the host's network stack.
- `SCOPE` is usually `local` for networks on this host only.

This output helps you confirm which networks exist and whether a container is using the default bridge or the host network.

## DNS and Service Discovery

Containers on user-defined networks can resolve each other by name using Docker's embedded DNS.

## Connecting and Disconnecting Containers

```sh
# Connect an existing container to a network
docker network connect my_bridge app3

# Disconnect a container from a network
docker network disconnect my_bridge app3
```
## Docker Volumes

Docker volumes persist data outside the container file system so data can survive container removal, upgrades, and restarts.

### Volume Types

- named volume: Managed by Docker, stored under `/var/lib/docker/volumes` on Linux. Good for persistent application data and stateful services.
- bind mount: Mounts a host directory or file into a container. The source is a path on the host machine, for example `$(pwd)/site`. Best for local development, configuration files, or sharing source code with containers.
- anonymous volume: Created by Docker when you mount a path without naming the volume. Useful for temporary data that should persist while the container exists.
- tmpfs mount: Stores data in memory only. Use for sensitive or ephemeral runtime data that should not be written to disk.

### Creating and Using Volumes

```sh
# Create a named volume
docker volume create app_data

# Run a container with a named volume
docker run -d --name mydb -v app_data:/var/lib/mysql mysql:latest

# Run a container with a bind mount from the host directory
docker run -d --name web -v $(pwd)/site:/usr/share/nginx/html nginx:latest
# Here, the host source directory is $(pwd)/site and the container target path is /usr/share/nginx/html

# Use the newer --mount syntax for clarity
docker run -d --name mydb --mount source=app_data,target=/var/lib/mysql mysql:latest
```

### Sharing Volumes Between Containers

```sh
docker run -d --name writer --mount source=shared_data,target=/data busybox sh -c "echo hello > /data/hello.txt"
docker run -d --name reader --mount source=shared_data,target=/data busybox cat /data/hello.txt
```

### Inspecting Volumes

```sh
docker volume ls
# List all Docker volumes

docker volume inspect app_data
# Show details about a specific volume
```

### Removing and Cleaning Up Volumes

```sh
docker volume rm app_data
# Remove a specific volume

docker volume prune
# Remove all unused volumes
```

### When to Use Volumes vs Bind Mounts

- Use **named volumes** for database data, logs, caches, and other production persistence.
- Use **bind mounts** for live development, mounting your source code or local config files into containers.
- Use **tmpfs mounts** for temporary data, session storage, or fast in-memory state.

### Best Practices

- Prefer Docker-managed named volumes for stateful services because Docker handles the lifecycle and path location.
- Avoid keeping important data only inside containers; containers are meant to be replaceable.
- Clean up unused volumes with `docker volume prune`, but only after confirming the volumes are no longer needed.
- Use `docker volume inspect` to debug where a volume is mounted and which containers use it.

### Example: Database Persistence

```sh
# Create a volume for PostgreSQL data
docker volume create pg_data

docker run -d --name postgres -e POSTGRES_PASSWORD=secret \
  --mount source=pg_data,target=/var/lib/postgresql/data \
  postgres:latest
```

Now the database data remains intact even if you remove and recreate the `postgres` container.
