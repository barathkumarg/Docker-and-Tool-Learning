# Docker Networking and Volumes

## 1. Docker Networking

### 1.1 Why it is used
- Containers need to communicate with each other, the host, and the internet.
- Each container gets its own network namespace and IP address.
- Networks isolate and organize services for security and manageability.

### 1.2 Network drivers (complete list)

| Driver | Description | Typical use |
|---|---|---|
| bridge | Default driver; private internal network on a single host | Standalone containers on one host |
| host | Removes network isolation; container uses host's network stack directly | High-performance networking, no port mapping needed |
| none | Disables networking entirely | Fully isolated/offline containers |
| overlay | Virtual network spanning multiple Docker hosts | Docker Swarm, multi-host clusters |
| macvlan | Assigns a real MAC address, making the container appear as a physical device on the network | Legacy apps expecting direct LAN access |
| ipvlan | Like macvlan but shares the host's MAC address, splitting by IP instead | Environments where MAC address limits apply |
| Custom plugins (Weave, Calico, Flannel) | Third-party SDN drivers | Kubernetes/Swarm advanced networking, policy enforcement |

### 1.3 Default vs user-defined bridge networks
- **Default bridge** (`docker0`): containers can only reach each other by IP; no automatic DNS resolution by name.
- **User-defined bridge**: built-in DNS server resolves container names automatically; better isolation; recommended for almost all multi-container setups.
- Always prefer creating a custom network over relying on the default bridge.

### 1.4 Basic commands
```sh
docker network ls                          # list all networks
docker network create my_net               # create a new bridge network
docker network create -d overlay my_ovl    # create an overlay network
docker network inspect my_net              # view detailed network info (subnet, gateway, connected containers)
docker network connect my_net container1   # attach a running container to a network
docker network disconnect my_net container1 # detach a container from a network
docker network rm my_net                   # remove a network
docker network prune                       # remove all unused networks
```

### 1.5 Creating networks with custom options
```sh
docker network create \
  --driver bridge \
  --subnet 172.20.0.0/16 \
  --gateway 172.20.0.1 \
  --ip-range 172.20.5.0/24 \
  my_custom_net
```
- `--subnet`: defines the IP range for the network.
- `--gateway`: sets the gateway IP.
- `--ip-range`: restricts which sub-range containers get IPs from.
- `--internal`: creates a network with no outbound internet access (fully isolated).
- `--attachable`: allows standalone containers to attach to a swarm overlay network.

### 1.6 Port mapping
```sh
docker run -d -p 8080:80 nginx          # host:container
docker run -d -p 127.0.0.1:8080:80 nginx # bind only to localhost
docker run -d -p 8080:80/udp nginx       # map a UDP port
docker run -d -P nginx                   # publish all exposed ports to random host ports
```
- `EXPOSE` in a Dockerfile only documents intent; it doesn't actually publish a port — `-p` or `-P` is required at runtime.

### 1.7 Container-to-container communication
```sh
docker run -d --name web --network my_net nginx
docker run -d --name app --network my_net myapp
```
- On a user-defined network, containers reach each other using their **container name** as a hostname.
- Use `--network-alias` to give a container additional DNS names on a network — useful for load-balancing across replicas.

```sh
docker run -d --name web1 --network my_net --network-alias web nginx
docker run -d --name web2 --network my_net --network-alias web nginx
# requests to "web" resolve to either web1 or web2 (round-robin DNS)
```

### 1.8 DNS and service discovery
```sh
curl http://web
```
- Docker's embedded DNS server (127.0.0.11 inside the container) handles name resolution on user-defined networks.
- Multiple networks can be attached to one container; it gets a separate IP and DNS entry per network.

### 1.9 Connecting a container to multiple networks
```sh
docker network create net1
docker network create net2
docker run -d --name multi --network net1 nginx
docker network connect net2 multi
```
Useful for a container that needs to act as a bridge between two isolated networks (e.g., an API gateway).

### 1.10 Inspecting and troubleshooting networking
```sh
docker inspect container_name | grep IPAddress     # find a container's IP
docker exec -it container_name ping other_container # test connectivity
docker exec -it container_name nslookup web         # test DNS resolution
docker port container_name                          # show published ports
```
- Common issues: containers on different networks can't see each other by default; firewall/iptables rules on the host can block bridge traffic; `host` network mode bypasses Docker's NAT entirely.

### 1.11 Docker Compose networking
- Compose automatically creates a default network for all services in a `docker-compose.yml`, and each service is reachable by its service name.
```yaml
services:
  web:
    image: nginx
  app:
    image: myapp
    depends_on:
      - web
networks:
  default:
    driver: bridge
```

### 1.12 Security considerations
- Use `--internal` networks for backend services (e.g., databases) that should never reach the internet.
- Avoid `--network host` unless performance truly requires it — it removes container network isolation.
- Limit published ports to only what's necessary; never expose database ports publicly.
- Use network segmentation (separate networks per tier: frontend, backend, database) to limit blast radius.

## 2. Docker Volumes

### 2.1 Why volumes are important
- Container filesystems are ephemeral — data is lost when a container is removed.
- Volumes decouple data lifecycle from container lifecycle.
- Best practice and most performant option for persisting data, especially for databases.

### 2.2 Volume types (complete comparison)

| Type | Managed by | Location | Persists after container removal | Use case |
|---|---|---|---|---|
| Named volume | Docker | `/var/lib/docker/volumes/...` | Yes | Databases, app data |
| Anonymous volume | Docker | Same as named, random ID | Yes (until pruned) | Temporary data Docker manages automatically |
| Bind mount | User | Any host path | Yes | Local development, sharing source code |
| tmpfs mount | Docker (in-memory) | RAM only, never written to disk | No | Secrets, sensitive temporary data |

### 2.3 Basic commands
```sh
docker volume create my_data       # create a named volume
docker volume ls                   # list volumes
docker volume inspect my_data      # show mountpoint, driver, labels
docker volume rm my_data           # remove a specific volume
docker volume prune                # remove all unused (dangling) volumes
docker volume prune -a             # remove all unused volumes, including named ones not in use
```

### 2.4 Using volumes — all syntaxes
```sh
# named volume (-v shorthand)
docker run -d --name db -v my_data:/var/lib/mysql mysql

# bind mount
docker run -d -v $(pwd)/app:/app nginx

# anonymous volume
docker run -d -v /var/lib/mysql mysql

# read-only mount
docker run -d -v my_data:/var/lib/mysql:ro mysql

# --mount syntax (more explicit, recommended for scripts/production)
docker run -d --mount source=my_data,target=/data nginx
docker run -d --mount type=bind,source=$(pwd)/app,target=/app nginx
docker run -d --mount type=tmpfs,target=/app/cache,tmpfs-size=64m nginx
```
- `--mount` is more verbose but explicit and catches typos (`-v` silently creates a volume if a name is misspelled; `--mount` will error instead).

### 2.5 tmpfs mounts in depth
```sh
docker run -d --tmpfs /app/tmp:rw,size=100m nginx
```
- Data exists only in memory, never touches disk.
- Lost when the container stops.
- Ideal for secrets, session data, or temp caching where persistence is undesirable.

### 2.6 Volume drivers and remote storage
- Default driver is `local`, but plugins enable cloud or networked storage:
```sh
docker volume create --driver vieux/sshfs \
  -o sshcmd=user@host:/path \
  -o password=mypassword \
  remote_vol
```
- Common plugins: NFS, sshfs, cloud-specific drivers (e.g., for AWS EBS, Azure Disk) for use in clustered/multi-host environments.

### 2.7 Backing up and restoring volumes
```sh
# backup a volume to a tar file
docker run --rm -v my_data:/data -v $(pwd):/backup busybox \
  tar czf /backup/my_data_backup.tar.gz -C /data .

# restore a volume from a tar file
docker run --rm -v my_data:/data -v $(pwd):/backup busybox \
  tar xzf /backup/my_data_backup.tar.gz -C /data
```

### 2.8 Sharing volumes between containers
```sh
docker run -d --name db -v shared_data:/var/lib/mysql mysql
docker run -d --name backup_tool --volumes-from db busybox
```
- `--volumes-from` mounts all volumes of another container — useful for backup/utility containers.

### 2.9 Volumes in Docker Compose
```yaml
services:
  db:
    image: mysql
    volumes:
      - db_data:/var/lib/mysql
  app:
    image: myapp
    volumes:
      - ./src:/app/src   # bind mount for live code editing
volumes:
  db_data:
```

### 2.10 Permissions and ownership
- Bind mounts inherit host file permissions/UID-GID, which can cause "permission denied" errors inside containers running as non-root.
- Fix with `--user $(id -u):$(id -g)` at runtime, or `chown` inside a Dockerfile build step.
- Named volumes are easier here since Docker manages ownership consistently.

### 2.11 Security considerations
- Avoid bind-mounting the Docker socket (`-v /var/run/docker.sock:/var/run/docker.sock`) unless absolutely necessary — it grants root-equivalent host access.
- Use `:ro` (read-only) mounts wherever a container only needs to read shared data, not write it.
- Use tmpfs for secrets instead of writing them to a regular volume or bind mount.
- Regularly prune unused volumes to avoid leaking sensitive leftover data.

## 3. Best Practices Summary
- Always use **user-defined bridge networks** instead of the default bridge for name resolution and isolation.
- Segment networks by tier (frontend/backend/db) and use `--internal` for backend-only networks.
- Use **named volumes** for persistent data like databases.
- Use **bind mounts** only for local development and live code reload.
- Use **tmpfs** for sensitive or temporary in-memory data.
- Prefer `--mount` over `-v` in scripts and production setups for clarity and error-checking.
- Regularly run `docker network prune` and `docker volume prune` to clean up unused resources.
- Never expose more ports than necessary; bind sensitive services to `127.0.0.1` instead of all interfaces.
- Avoid `--network host` and Docker socket mounts unless there's a strong, specific reason.
- Back up named volumes regularly using the tar-based backup pattern.

## 4. Full Example (Networking + Volumes Combined)
```sh
# Create an isolated backend network and a frontend-facing network
docker network create --internal backend_net
docker network create frontend_net

# Create a named volume for persistent database storage
docker volume create app_data

# Database — only on backend network, no internet access
docker run -d --name db \
  --network backend_net \
  -v app_data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=secret \
  mysql

# App — connects to both networks (talks to db, exposed to outside)
docker run -d --name app \
  --network backend_net \
  myapp

docker network connect frontend_net app

# Web server — front-facing, port mapped, with bind mount for live config
docker run -d --name web \
  --network frontend_net \
  -p 8080:80 \
  -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx
```
